# 模板：负向验收（negative-path）

**适用**：任何“检查/验收/门禁”类任务。

**为什么**：只测 happy path 的门禁，等于没有门禁。必须证明“该拒绝的确实被拒绝”。

## 做法

在契约的 `negative_acceptance` 中显式列出反向用例，例如：

| 用例 | 期望 |
|---|---|
| 引用不存在的证据路径 | 拒绝 |
| 行号越界 | 拒绝 |
| 引文与原文不匹配 | 拒绝 |
| 退出码为 0 但产物缺失 | 判 failed |
| 结构化结果合法但必填字段缺失 | 判 failed |
| 重复执行同一已完成的步骤 | 不重复产生副作用 |

## 步骤

1. 先列出“什么情况必须失败”，再写正向验收；
2. 每个负向用例准备可复现的输入（fixture）；
3. 用与正向相同的校验器执行，不允许为负向用例开后门；
4. 记录实际结果与期望是否一致，不一致即门禁不成立；
5. 把负向用例固化进自动化测试，防止后续改动把失败包装成成功。

## 验收

- 负向用例 100% 按预期失败，且失败原因可读；
- 校验器对伪造证据、缺失产物、畸形结果一致地拒绝；
- 负向用例进入 CI，而不是一次性人工演示。

## 常见失败

- 只打印“已检查”，没有期望值；
- 负向用例与正向走不同代码路径 → 测不到真实门禁；
- 失败被 catch 后吞掉，最终仍显示成功。
